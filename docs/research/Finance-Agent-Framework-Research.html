End-to-End Finance Agent Architecture

1. Executive assessment

Recommendation. Build a finance platform with deterministic accounting and transaction services, durable process orchestration, and stable, bounded that use a versioned library. Allow to interpret, investigate, propose and coordinate. Let tested services calculate, validate and execute. Expand automatic execution wherever an action has sufficiently clear inputs, policy, evidence and recovery behaviour.

The intended destination is end-to-end coverage: operational transactions become accounting, actuals feed planning, and handle the routine work and much of the exception work. This does not require a at every step, a permanent for every activity, or one enormous shared prompt. Shared execution components can support many process-specific without duplicating infrastructure. Routine work and known exceptions use named, versioned, signed-off and . Case-specific is reserved for supervised novel investigations, whose proposals have no production authority.

Three foundations should remain stable as models improve: the company's financial meaning and records; its authority and control rules; and the interfaces through which work is requested, executed and verified. Model selection, prompts, techniques and frameworks should be replaceable behind those interfaces. No architecture is literally future-proof; this design makes the expensive financial foundations less dependent on rapidly changing components.

Public evidence supports composable , selective autonomy, progressive context loading and disciplined . It does not establish that a general-purpose framework can autonomously operate an entire enterprise finance function with reliable accounting and controls. Anthropic distinguishes fixed from model-directed and recommends adding complexity when needed. OpenAI's practical guide similarly recommends establishing quality first and then substituting cheaper models where support it.12

The strongest initial architecture is an -connected implementation with a custom evidence, and analytical layer. A custom financial is a valid second mode, but it brings the responsibilities of a finance software product: subledgers, accounting rules, period management, consolidation, operational support, local requirements and migration assurance. Build the common contracts so either mode can be selected by entity and accounting domain.

A is finance software you build yourself to store transactions, perform accounting calculations, maintain the ledger and support reporting and planning.

The operating discipline in section 6 governs how are configured, improved and authorised. It sits within the architecture alongside context management, financial records, integration, recovery, security and cost management.

Proposed context assembly

Before an agent starts a task, the system gathers the instructions, rules and evidence it needs without loading the entire library.

First determine from trusted task metadata: , entity, jurisdiction, accounting basis, book, business date, reporting period, product and permitted actions. If these are unknown and affect the answer, resolve them before committing a financial decision.

Next resolve mandatory policies through explicit applicability rules and dependency links. A journal can require period rules, journal authority, accounting treatment and currency rules regardless of the 's search choices. Exact identifiers and versions select these documents. Semantic search supplements this mandatory set with relevant examples, explanations and optional procedures.

Use hybrid : metadata filters and for account codes, policy numbers and precise terms; for conceptual similarity; reranking where it demonstrates benefit. Retain clause-level and the surrounding definitions, exceptions and tables. A chunk that says a payment is allowed is unsafe if its adjacent exception prohibits a recently changed bank account.

Return a listing what was loaded, the release, versions, effective dates, hashes, missing prerequisites and unresolved conflicts. Save this with the decision. Summaries can help navigation but must link to authoritative text; they must not replace an exact threshold or an exception clause.

The proposed first working budget is 12,000-32,000 input for ordinary reasoning tasks, with larger budgets reserved for demonstrated need. This is an initial engineering hypothesis, not a universal optimum. Measure task success against context size, latency, cost and omitted-policy failures. The mandatory control set must not be silently truncated to meet a budget.

Policy lifecycle and conflicts

The system must identify which rules apply and what to do when rules change or disagree.

Give every policy an owner, approval status, jurisdiction, accounting basis, applicability predicate, valid-from and valid-to dates, recorded-at date, superseded-by reference and dependency list. Store the human-readable source and the implemented decision rule separately, with a traceable relationship and independent validation of the translation.

Define an approved precedence scheme for legal requirements, accounting standards, group policy, entity policy and explicit exceptions. Do not assume the most recent file wins. A local rule can supplement a group rule or create a conflict requiring adjudication. Unknown , conflicting mandatory rules and expired exceptions should stop the affected action and create a resolvable case.

A policy change triggers dependency analysis across the named roster, reindexing, and a new released policy bundle. Record the affected / releases and their renewed sign-off or approved compatibility decision. Never let a shared update silently change every that references it. Existing tasks retain their original evidence, but the checks whether a current restriction or revocation prevents execution. For historical accounting, distinguish rules applicable to the transaction date from present-day action authority.

Agents need to retain useful progress and approved lessons without treating every past answer as a reliable fact.

Keep task notes, approved business facts and policy in different stores. An 's previous answer is not a new accounting policy. Attach feedback to the responsible , release and case. Known exceptions are part of the standard operating model

Expected problems should have established handling procedures even when the individual case is new.

An exception specifies its trigger, eligibility, assigned standard , data requirements, investigative steps, permitted remedies, mandatory human decisions, limits, deadlines and completion evidence. Version and test it with the routine . The can use bounded reasoning to investigate without improvising new authority or changing the process.

For example, a receipt mismatch triggers a standard request for evidence and a hold. An ambiguous payment response triggers destination reconciliation. A material coding dispute goes to the designated accountant. These are expected operational cases even when their specific facts are unique. Technical retries, low confidence, high value and unavailable data are not automatic evidence of a novel exception.

Unclear coverage enters a human triage queue. The standard retains case ownership and the original transaction stays in its controlled . Higher-precision valuation engines may use different numerical techniques, but their conversion into accounting amounts must be controlled and tested.18

For a first implementation, PostgreSQL plus object storage is a reasonable design choice: relational data supports joins and constraints, while documents and calculation artefacts reside outside prompts. A specialised ledger such as TigerBeetle is worth evaluating if transfer volume and balance constraints justify it. Its immutable transfer model and correction pattern are useful, but it is not a complete general ledger, consolidation or tax application.19

Time, closing and corrections

The system must distinguish when events happened, when they were recorded and which reporting period they affect.

Distinguish when an happened, when it was received, the accounting date, the effective policy date and the reporting snapshot. This supports late invoices, corrections, restatements and as-known-at analysis. A closed period cannot be changed merely by backdating an . The configured accounting treatment determines whether a current-period adjustment or authorised reopening is appropriate.

A live economic view can continuously incorporate new information. A certified reporting snapshot fixes the included data, rules and mappings for a reporting cycle. Label the status of every report: provisional, reconciled, certified or superseded. Continuous processing does not eliminate cut-off, estimates, certification or independent audit.

For insurance, add contract/cohort/group identifiers, approved measurement models and links to actuarial assumptions. Keep valuation engines deterministic or reproducibly stochastic. can assemble inputs, investigate movements and explain results; they do not improvise IFRS 17 measurements. A preferred common economic view can coexist with explicit statutory, regulatory and management adjustments; the architecture must not assume all reporting bases are identical.

9. Actuals, budgets, forecasts and stress testing

Use common definitions for entity, account, product, customer, cost centre, period, currency and measure. Record hierarchy and mapping versions so a reorganisation does not silently rewrite historical comparisons. Build a semantic layer of approved metrics and queries that both and reporting use.

Actuals are accepted posted facts. A budget is an approved plan version. A forecast is a dated estimate using a defined baseline. A scenario is a conditional set of assumptions; a sensitivity isolates a parameter change; a stress scenario examines severe combinations and constraints. These can share models and dimensions without sharing write authority.

A stable Forecast Preparation runs the signed-off forecast process, including recognised exceptions such as missing drivers or failed reconciliation. Unfamiliar scenario values do not make the process novel when they fit the approved model and limits. A new causal method, unsupported accounting treatment or unvalidated model requires a supervised investigation; its outputs stay separate from official forecasts until adopted.

The recommended analytical process is: freeze the actuals baseline; validate operational drivers; obtain approved or explicitly provisional assumptions; execute the quantitative engine; reconcile movements and balances; generate explanations linked to outputs; then approve or publish the plan version. help elicit assumptions and detect missing drivers. Deterministic code owns arithmetic, allocation, currency treatment and aggregation.

For example, a supplier disruption scenario can change unit costs, available capacity and delivery times. A driver model translates these into revenue, costs, inventory, receivables, payables and cash. If capacity queues matter, a can provide throughput and delay distributions, which then feed the financial model. An describing a plausible disruption is not itself a validated simulation.

require model version, input snapshot, distribution assumptions, seed strategy and numerical tolerances. Reproducibility means being able to regenerate or explain the result under those specifications; it does not mean the future becomes certain. Stress tests should capture dependencies, correlations, liquidity constraints and management actions, rather than merely applying a percentage to every line.

Use backtesting, forecast-error analysis, bias checks and baseline comparisons to decide which quantitative models earn deployment. Keep observational data and management targets distinct: a target does not become the expected outcome because an repeats it. Where a scenario is impossible under its constraints, the engine should report infeasibility rather than manufacture a balanced-looking answer.

10. Reliable execution and recovery

Work must survive failures and restarts without disappearing or creating duplicate financial actions.

Temporal documents the need for idempotent activities because execution may be retried. 's pattern addresses the gap between saving a database change and publishing its notification. Neither removes the need to make external financial effects safe.2021

Use a durable for business processes that wait for approvals, survive failures and span hours or days. On resumption, recover the exact / release and case . Never restart by asking an to reconstruct the . Where an old release is revoked or cannot continue, hold the case for an explicitly approved migration or manual continuation. Record nondeterministic model and external-service calls as activities with persisted results. Deterministic replay must use those recorded results rather than ask a model to recreate its previous reasoning.

Inside the owned database, a single transaction can commit the accepted financial change, its evidence references and an outbox . Consumers deduplicate and apply . Partition ordering by the affected business object where relevant; avoid assuming a timestamp alone establishes a safe global sequence.

Across an or bank boundary, use a persistent record and a stable business key. Bind the key to canonical request parameters. Reusing a key with different parameters must fail. A lost response produces an , not an automatic failure. Query the destination using the reference before retrying. If uniqueness cannot be established, hold the work for investigation.

Approval must bind to the exact version and material parameters. A changed payee, amount, entity or bank account invalidates the earlier approval. Revalidate live permissions, period status and restrictive policy at commit time. Where relevant, apply aggregate limits across batches and related requests to prevent splitting a large action into individually acceptable amounts.

is business-specific. A posted journal can often be reversed, preserving history. A bank transfer may need a recall request and may not be recoverable. Do not promise universal rollback through a generic mechanism. Design unknown-outcome and remediation explicitly.

Use deadlines, retry classes, backoff, , reconciliation queues and clear ownership. Known failures follow signed-off exception ; failure of that route creates a human escalation, not permission for dynamic autonomous remediation. Infrastructure errors can retry; missing facts and policy disagreements need different resolution paths. A task should end in a verified outcome or an explicit blocked/failed case, never an apparently successful chat message with unfinished downstream work.

12. and operating cost

Choose the least expensive proven way to perform each task, using a model only where it adds value.

The proposed execution ladder within each signed-off is: no model; specialised small model; stronger general model; human judgement. Permitted model choices and escalation triggers form part of its approved release. A more capable model does not expand the 's remit or convert a novel exception into an authorised . Route by task and risk, not an 's title. Extraction and classification often need a different profile from contract interpretation or a complex investigation. A difficult document may require a more capable vision model even when the downstream accounting is entirely deterministic.

NVIDIA researchers argue for small models on repetitive, narrow tasks and heterogeneous systems where general reasoning remains necessary. This is a position supported by technical arguments, not a universal cost guarantee. OpenAI's guide recommends establishing a strong baseline and then testing smaller replacements. Both support -led routing rather than choosing the cheapest model in advance.252

Use quality signals such as extraction-field accuracy, source coverage, validity, reconciliation results, task novelty, missing evidence and out-of-distribution indicators. Self-reported confidence is not a calibrated probability. Define a bounded escalation path: retry only repairable failures; send difficult interpretation to a stronger approved model; route unresolved judgement to a human.

Separate inference, quantitative compute, document processing, infrastructure, data storage, monitoring, licences, engineering support and human review. A low bill can coexist with an expensive and unreliable service. Conversely, a stronger model may lower total cost by reducing exceptions and rework.

Illustrative workload calculation

This example separates model-call costs from the often larger cost of human review.

This example uses assumed all-in model-call costs, not current vendor prices or a forecast. For 100,000 monthly items, assume all items incur one small extraction call at £0.01. Of these, 10% additionally require a £0.10 investigation; 1% additionally require a £0.50 advanced interpretation. All three call types belong to signed-off routine or known-exception . Model cost is £1,000 + £1,000 + £500 = £2,500. The call classes are additive, and escalation populations can overlap.

If 5% of items then require ten minutes of human review at an illustrative £60 per productive hour, review costs £50,000. At 2%, the corresponding figure is £20,000. These are scenario assumptions, not an automation claim. They show why exception quality and human effort can dominate inference economics.

Budget novel investigations separately for human sponsorship, analysis, review and any subsequent implementation. They are excluded from the preceding illustrative volumes and cannot be counted as automatically resolved transactions merely because a draft was produced.

Measure cost per correctly completed item and per exception resolved, alongside median and . Attribute results to the persistent , release and work class; track approval latency and unresolved known exceptions separately from novel investigations. Track retries, discarded work, costs, cache misses and child- spend. Cache stable approved context and reusable results only with correct , version, and expiry keys. Batch non-urgent work when acceptable. Do not cache an approval decision past its validity.

Self-hosting a smaller model becomes attractive only when volume, utilisation, security constraints and operational justify it. Compare the full cost of capacity, resilience, upgrades and monitoring against hosted use. Avoid locking the design to a current model name or headline price; keep model profiles and dated rate cards as replaceable configuration.

14. and release gates

Before a change goes live, test that it produces correct outcomes and respects the required controls.

Evaluate routine , known-exception and novel investigations separately. For approved operations, an acceptable result is the correct financial and operational with the required evidence. For novel investigations, success means a useful, evidenced, clearly provisional deliverable and completion of the required human reviews, without unauthorised decisions or actions. A draft is not a resolved financial outcome. Test both completion and refusal: the must perform authorised work and correctly stop prohibited or underspecified actions. Anthropic's guidance distinguishes tests from regression protection and explains why repeated-trial consistency matters.32

Use an initial expert-labelled covering ordinary work, edge cases, missing data, contradictory policies and adversarial documents. Expand it with production failures. Keep a that is not available to prompt or optimisation. A test generator can assist, but finance experts must validate expected accounting and policy outcomes independently of the implementation.

15. Staged build plan

Build and verify one complete process first, then extend the system in manageable stages.

Stage 0: and financial contracts. Choose one entity, accounting basis, ledger authority and source-to-outcome process. Define finance meanings, permissions, acceptance tests and synthetic fixtures. Register the first process , release owners and approved exception coverage. Create a , policy registry and a short architecture decision log. Do not begin by importing thousands of pages without an ownership and applicability model.

Stage 1: one complete process using fixed rules. Implement source ingestion, validation, measurement, balanced posting in a test finance system, trial balance and a fixed reporting snapshot. Add outbox delivery, reconciliation and failure recovery. Provide a mock using the same contracts. The process should work with models disabled for structured inputs. Record the / release across retries and restarts.

Stage 2: bounded interpretation and context. Add invoice extraction or document classification; implement and selective . Introduce standard exception , the human case queue, evidence views and measured escalation. Prove that an adversarial document cannot change permissions or bank data.

Stage 3: complete process and proof. Extend invoice-to-payment through scheduling, approval, simulated settlement and cash reconciliation. Test one real , including accepted-versus-posted and timeout ambiguity. Promote live financial writes only after the operational and finance owners accept the evidence.

Stage 4: close and planning. Add recurring journals, reconciliations, period closure, actuals snapshots and a simple driver-based forecast. Demonstrate a scenario with P&L, balance-sheet and cash impacts that reconcile. Introduce consolidation and additional subledgers as separate releases.

Stage 5: supervised novel investigations. Introduce human-sponsored temporary , plan validation, scoped evidence and calculations. Keep outputs clearly provisional; enforce no direct or delegated production authority. Test review , separate action , shared budgets, expiry and circular delegation. Reusable improvements enter the normal development and release process.

Stage 6: expansion and optional finance system migration. Add entities, local policies, operational systems and specialist accounting. Validate restore, recovery objectives, throughput, access administration and support procedures. Use feedback and recurring cases to improve standard through evaluated, signed-off releases. Move ledger authority only when migration and reconciliation evidence justify it.

Avoid promising a time or budget for full enterprise coverage before , team, transaction volumes, local requirements and integration access are known. A demonstrator can be small; an enterprise is a substantially larger commitment. Cost reduction should be measured against work that passes production gates and remains stable.

16. Decisions to carry into the repository

Adopt the separation between deterministic financial services and replaceable reasoning. Adopt controlled context assembly and bundles. Adopt one posting authority per , immutable posted records, reproducible scenarios and independently enforced permissions. Adopt explicit unknown-outcome handling and evidence-based completion.

Keep framework choice, model providers, engines and hosting portable. Treat a new case as another execution of an approved , an operational configuration change as a controlled release, and a novel as a supervised investigation plan. Retain , feedback and performance history across releases. Defer autonomous policy changes, unrestricted self-improvement and multi- debate as a default control.

The first demonstrable outcome should connect a source transaction to a verified posting, a standard exception with human escalation, a reporting snapshot and a forecast input. That single path tests the foundation needed by the broader finance suite. Subsequent domains should reuse its control, context, data and execution contracts. Novel findings require separate acceptance and action authority; recurring resolutions can become approved after testing and sign-off.

Open implementation decisions are the first and accessible ; initial accounting ; transaction volume and service objectives; company-approved policies and source rights; quantitative engines already available; deployment and data-residency constraints; and accountable finance/engineering owners. These determine delivery effort without changing the central architecture.

HTTP
Hypertext Transfer Protocol, commonly used for service requests. A successful HTTP response need not mean the business action completed.
ID / URI
Identifier / uniform resource identifier, used to name records or locate resources.
MCP
Model Context Protocol: interfaces through which applications expose tools and resources to AI systems.
OWASP
Open Worldwide Application Security Project, a source of application and agent security guidance.
Finance workbench
The screen people use to see cases, evidence, outstanding work and approvals, make decisions and track progress. It provides access to the underlying workflows and financial records.
Bounded agent runtime
The software that runs the agent's code, including its calls to models and tools, while enforcing limits on permissions, time and spending. The agent calls the model; the runtime is how that code executes, not a separate decision-maker.
Policies, skills and definitions
The controlled knowledge libraries: policies specify required rules; skills provide reusable instructions and resources; definitions establish what financial terms and data fields mean. Agents load the authorised parts needed for their task.
ERP adapter
Integration software translating common finance requests into the ERP system's specific interfaces, fields and statuses. It returns destination references and status evidence so a submitted request is not mistaken for a completed posting.
Authoritative records
The designated financial records treated as the accepted source of truth, such as posted journals and certified snapshots. These reside in the ERP or Custom-built finance system selected for that scope; there must not be competing posting authorities.
Reconciliation and evidence
Checks that the intended financial result actually occurred, comparing receipts and source information with destination records. It preserves supporting evidence and returns verified completion or a case requiring attention to the workflow.
Work intake and scope
Receives a request or business event, creates a tracked work item and establishes its authorised boundaries, including entity, book, process, dates and purpose.
Approved workflow routing
Rules that select an approved workflow and agent release for a case. Routing can use validated classification, but cannot invent a new authorised process when no approved route fits.
Signed-off standard agents
Stable, named agents using tested and approved configurations. Their releases specify responsibilities, skills, tools, model choices and limits for routine work and recognised exceptions.
Known exception workflows
Approved procedures for expected problem types, such as missing receipts or an uncertain posting response. They define investigation steps, permitted remedies, human decisions and completion evidence.
Controlled command gateway
The enforced checkpoint before a production action. It validates the requesting identity, applicable approvals and financial conditions; temporary novel-investigation agents have no authority to use it for production actions.
ERP or custom-built finance system
The operational destination for approved financial commands: an existing ERP through its adapter, or the framework's own finance services. The chosen system is authoritative for the defined scope.
Human triage and sponsorship
A person decides whether an unresolved case fits an existing approved route. If it requires a novel investigation, a named sponsor approves the question, participants, evidence access, limits and review checkpoints.
Supervised novel investigation
A temporary, human-directed investigation of a case outside approved coverage. It may combine skills or agents to analyse evidence and prepare proposals, but cannot make binding decisions or execute production financial actions.
Labelled proposals and human review
Investigation findings, assumptions and suggested decisions are visibly marked as provisional. An accountable person reviews them; accepting the findings does not by itself authorise their execution.
Separate controlled adoption
The explicit step after review that authorises a particular action through an approved workflow or manual process. Making the solution reusable requires separate development, testing and release sign-off.
Typed
Having a defined data format, so software can check that inputs and outputs contain the expected fields and value types, such as text, dates or numbers. Passing this check does not by itself prove that the information is correct.
Polling
Checking repeatedly whether work is available, for example checking every ten seconds for items in an eligible state. Ordinary deterministic code can perform this check; no LLM call is needed.
Execution loop
The repeated steps in an agent's execution: call the model when needed, carry out permitted tool requests, return results and continue until completion or a stopping limit. An execution loop implemented in your own code is maintained by your team rather than supplied by an agent toolkit.
Custom-built finance system
The finance software you build yourself to store transactions, perform accounting calculations, maintain the ledger and support reporting and planning, instead of relying on an ERP for those functions.
